# EH Home — Phase 45: Production Release, Deployment & Distribution Readiness

## 1. Executive Summary

Phase 45 establishes a deterministic, secure, reproducible release and deployment system for the EH Home platform. It unifies release engineering across:
- **Backend Services & Docker Artifacts**
- **PostgreSQL Database Schema & Migration Gates**
- **Flutter Consumer Application**
- **ESP32 Firmware Binaries & OTA Distribution**
- **SBOM (Software Bill of Materials) Inventory**
- **Pre-deployment Verification Gates, Post-deployment Health Probes & Safe Rollback**

## 3. Explicit Release Lifecycle State Machine

```
  ┌─────────┐
  │  DRAFT  │
  └────┬────┘
       │ [run automated validation suite]
       ▼
 ┌───────────┐      [validation failed]      ┌──────────┐
 │ VALIDATED ├──────────────────────────────►│ REJECTED │
 └─────┬─────┘                               └──────────┘
       │ [approval to candidate]
       ▼
 ┌───────────┐
 │ CANDIDATE │
 └─────┬─────┘
       │ [explicit promotion to channel]
       ▼
 ┌───────────┐
 │ PUBLISHED │
 └─────┬─────┘
       │ [deployment prechecks + health gate pass]
       ▼
 ┌───────────┐      [health probe failure]     ┌────────┐
 │ DEPLOYED  ├────────────────────────────────►│ FAILED │
 └─────┬─────┘                                 └───┬────┘
       │ [superseded by newer release]             │
       ▼                                           │ [safe rollback]
┌────────────┐                                     ▼
│ SUPERSEDED │                              ┌─────────────┐
└────────────┘                              │ ROLLED_BACK │
                                            └─────────────┘
```

## 4. Pre-Deployment Gates & Post-Deployment Verification

### Pre-Deployment Checks
1. **Lifecycle Status**: Release must be in `PUBLISHED` (or `CANDIDATE`) state.
2. **Database Schema Parity**: Matches expected schema version (`029`), with migration symmetry verified.
3. **Configuration Safety**: Rejects development defaults (`ALLOW_DEV_DEFAULTS=true`) or test database connections in production.
4. **Artifact Checksums**: Verifies SHA-256 digests of all released binary and container artifacts.

### Post-Deployment Health Probes
- Liveness Probe: `GET /health/liveness`
- Readiness Probe: `GET /health/readiness`
- Database Connection Probe: Verifies active pool connectivity.
- Failure of any probe marks the deployment as `FAILED` and blocks traffic routing.

---

## 5. Safe Rollback Policy

- Rollback must target an existing, validated release in `SUPERSEDED` or `PUBLISHED` state.
- **Database Safety**: Schema migrations are forward-compatible; destructive automatic down-migrations are blocked in production.
- **Firmware Safety**: Enforces Phase 35 cryptographic anti-rollback checks (target firmware version $\ge$ active firmware version or explicitly authorized cryptographic downgrade).
- **Audit & Metrics**: Records complete rollback reasons and emits deployment metrics.

---

## 6. Physical Validation Boundary & Disclaimer

> [!IMPORTANT]
> **SIMULATION & TESTING BOUNDARY**:
> 1. **Software Release Validation**: All CI/CD build scripts, Docker packaging, migration verifications, and unit/widget/integration tests have passed.
> 2. **Physical Hardware & App Store Qualification**:
>    - Apple App Store & Google Play Store distribution approvals require live vendor console review.
>    - Physical ESP32 silicon flash endurance, antenna RF qualification, and mass factory batch flashing are tested in software simulation; final physical hardware-in-the-loop qualification is scheduled on factory test fixtures.

## 7. Verification Matrix (30/30 Scenarios)

The test suite `backend/tests/phase45-production-release.test.js` covers 30 complete release engineering scenarios:
1. Release metadata validation (required fields & structure)
2. Semantic version validation (SemVer 2.0.0 compliance)
3. Source commit metadata (40-char SHA tracking)
4. Release lifecycle transitions (`DRAFT` → `VALIDATED` → `CANDIDATE` → `PUBLISHED` → `DEPLOYED` → `SUPERSEDED`)
5. Invalid release rejection (blocks illegal state jumps)
6. Artifact checksum validation (SHA-256 integrity verification)
7. Artifact signature metadata validation (Ed25519 metadata)
8. Release manifest validation (canonical schema, zero secrets)
9. Channel promotion rules (explicit channel assignment)
10. Migration release gate (validates schema version 029)
11. Production configuration validation (rejects dev configs)
12. Environment separation (rejects test `NODE_ENV` in production)
13. Deployment precheck (all gates must pass before deploy)
14. Health-gated deployment (verifies healthy response)
15. Deployment failure handling (marks release as `FAILED` if health check fails)
16. Rollback authorization (`ADMIN` only, restores target release)
17. Invalid rollback rejection (rejects non-existent or invalid target)
18. Firmware artifact compatibility (anti-rollback & hardware profile)
19. Flutter release metadata (version, build number, platforms)
20. Secret scanning / release safety (zero secrets in release manifest)
21. SBOM / dependency inventory association (SPDX-JSON linkage)
22. Audit integration (records lifecycle transitions)
23. Observability integration (records deployment metrics)
24. Incident correlation (links failed deployments to incident metadata)
25. Release RBAC (non-admin cannot publish or deploy)
26. Artifact reproducibility metadata (toolchain, node version)
27. Post-deployment health verification (executes probe)
28. Release candidate promotion (`VALIDATED` → `CANDIDATE`)
29. Production promotion gate (explicit promotion action)
30. Release regression / integrity verification (deterministic manifest generation)
