Factory Reset Nested Screen Implementation Plan

When the user taps:

Settings → Factory reset

this should open a dedicated Factory Reset / Reset Home flow.

This is the most sensitive action in the Settings area. It must be intentionally slower, explicit, authenticated, and impossible to trigger accidentally.

The screen should clearly explain what will be reset, what will remain, what the user must do first, and whether the action affects the physical device, the EH Home configuration, or both.

1. First: Define What “Factory Reset” Actually Means

Before implementation, do not use the term “factory reset” for multiple different operations.

Your system can potentially have three different destructive operations:

1. Reset physical device
2. Remove device from this home
3. Remove/reset the entire home

These are not the same.

Physical device reset
ESP32 / device
→ erase configuration
→ remove Wi-Fi credentials
→ remove pairing/configuration
→ restore factory defaults
Remove device from home
Home
→ remove device relationship
→ device may remain configured physically
Reset entire home
Home
→ remove home configuration
→ remove device associations
→ remove memberships/invitations
→ reset supported home settings

Your current Settings label says:

Factory reset — Remove this home from the device

That wording is ambiguous.

For production, I recommend changing the main action to one of these, depending on the actual backend behavior:

If it resets the physical device:

Factory reset device

If it removes the home relationship:

Remove home from this device

If it resets the entire EH Home:

Reset this home

Do not use one phrase for three different behaviors.

3. Initial Screen — Strong Warning

The first screen should not immediately show a large destructive button without explanation.

Recommended:

←   Factory reset

Then a warning card:

┌─────────────────────────────────────┐
│              !                      │
│                                     │
│        Reset your device            │
│                                     │
│ This will remove the current home   │
│ configuration from the device.     │
└─────────────────────────────────────┘

Use a restrained destructive visual treatment.

Avoid making the entire screen bright red. That looks alarming rather than professional.

4. Explain Exactly What Will Happen

Section:

WHAT WILL HAPPEN

Example:

✓ The device's home configuration
  will be removed.


✓ Wi-Fi configuration will be removed.


✓ The device will return to setup mode.


✓ You will need to set up the device again.

Then:

WHAT WILL NOT HAPPEN

If applicable:

• Your EH account will not be deleted.
• Other homes will not be affected.
• Other devices will not be reset.

These statements must be based on the actual implementation.

Do not claim that something is preserved if the backend actually deletes it.

6. Show Dependencies

Before resetting, determine whether there are dependencies.

Example:

• 2 routines

Then:

This is important for EH Home because your Routines architecture explicitly references devices.

7. Routine Impact

If a device being reset is referenced by routines:

3 routines use this device


Plant care
Kitchen alert
Night mist


These routines will remain saved, but
their actions may become unavailable
until the device is connected again.

This is much better than silently breaking routines.

Important rule

Do not automatically delete routines just because a device is reset.

The routines should move to an unavailable state where appropriate:

Plant care
⚠ Action unavailable
Mist maker needs to be set up again.

That is consistent with your existing Routines architecture.

8. Activity Impact

Factory reset should also be explicit about Activity.

Example:

ACTIVITY HISTORY


Previous activity records will remain
available unless you choose to delete them.



Or, if the actual operation removes them:

Activity history related to this device
will be removed.

Again, this must match the actual data behavior.

Don't automatically assume reset means history deletion.

9. Security Requirement

This action should require strong confirmation.

Do not allow:

Tap reset
→ immediately execute

Recommended:

Reset
 ↓
Confirm identity / authority
 ↓
Confirm exact scope
 ↓
Optional physical-device authorization
 ↓
Execute

At minimum, the backend should verify that the current user has sufficient permission.

For home management:

Owner

or another explicitly authorized role should be required.

A regular member should not be able to factory-reset the home/device simply because they can open Settings.

10. Physical Device Authorization

For a real ESP32 product, a high-risk destructive action may require stronger authorization than a normal UI action.

Depending on the actual architecture, this might be:

Authenticated account
+
Secure device session
+
Physical-device confirmation

For example, the UI could ask the user to:

Press and hold the device button for 5 seconds to confirm reset.

Only implement this if the firmware actually supports it.

Do not create a UI claiming there is a physical confirmation mechanism unless the ESP32 firmware implements it.

12. High-Risk Final Confirmation

For a destructive action, require deliberate confirmation.

Example:

Confirm factory reset


Type:


RESET


[ RESET                      ]


[ Cancel ]


[ Factory reset ]

The button remains disabled until the required confirmation is entered.

This is appropriate for a true device factory reset.

For a less destructive "remove device from home" operation, typing RESET may be excessive.

The confirmation level should match the actual risk.

13. Better Alternative for Device Reset

For a consumer product, you can also use:

Press and hold to confirm

but only if the interaction is technically reliable and accessible.

A text-confirmation step is often easier to make deterministic.

15. Repository Architecture

Create a dedicated boundary:

ResetRepository
├── getResetImpact(scope)
├── validateResetAuthorization(scope)
├── requestPhysicalConfirmation(scope)
├── beginReset(scope)
├── getResetProgress()
├── cancelReset()
└── verifyReset()

Potential result types:

success
unauthorized
unsupported
unavailable
confirmationRequired
inProgress
failed
timeout
cancelled
verificationFailed

This lets the UI behave correctly in every state.

16. Reset Scope Model

Define the scope explicitly.

ResetScope
├── device
├── home
└── configuration

Then:

ResetRequest
├── scope
├── targetId
├── initiatedBy
├── confirmation
└── authorization

This prevents accidentally calling a generic:

reset()

that has unclear semantics.

17. Reset Impact Model

Before execution:

ResetImpact
├── target
├── devicesAffected[]
├── routinesAffected[]
├── roomsAffected[]
├── peopleAffected[]
├── activityImpact
├── dataDeletionImpact
└── requiresPhysicalConfirmation

Then the UI can render a truthful summary.

19. Physical Device Reboot

For the ESP32:

Please keep it powered on.

The user shouldn't unplug the device during that process.

Do not unplug the device yet.

[ Get help ]

Final production principle

For this screen, the most important rule is:

Never tell the user that a reset completed until the physical device/backend state has been verified.

So:

Reset command sent
        ≠
Reset successful

and:

Device rebooted
        ≠
Factory state verified

Only:

Command
 ↓
Device reset
 ↓
Device responds
 ↓
Factory-default state verified
 ↓
UI = Reset complete

That approach keeps the Factory Reset flow consistent with the same production-grade reliability rules you have already established for Routines, Activity, Home Connection, Device Health, and Settings.
