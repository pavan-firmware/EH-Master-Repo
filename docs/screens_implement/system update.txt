System Update Nested Screen Implementation Plan

When user taps:

Settings → System update

open one reusable:

SystemUpdatePage

Purpose:

Check, understand, and safely install EH Home software/firmware updates.

This screen should support app updates, Hub firmware, and Node/device firmware later, but current implementation should show only update types that actually exist.

Settings

SystemUpdatePage

14. Failed Update

This needs serious handling.

Update couldn't be completed


Your device is still running
its previous firmware.


No changes were made to your
current working version.


[ Try again ]


[ Get help ]

Never tell the user:

Update failed

without explaining whether the existing firmware remains safe.

For OTA systems, rollback/boot selection should ensure the previous working image remains usable where supported.

15. Device Offline During Update
Update paused


Your device went offline.


Reconnect the device to continue.


[ Try again ]

Don't automatically keep retrying forever.

16. Low Power / Power Safety

If the device is battery-powered:

Update unavailable


Battery level is too low.


Charge the device before updating.

If your device is mains-powered, don't display battery checks that don't apply.

Again:

UI must follow actual product capability.

17. Network Failure
Couldn't download the update


Check your internet connection
and try again.


[ Retry ]

If firmware is transferred locally from phone to Node, the error model changes accordingly.

Don't hard-code cloud assumptions.

24. Security Rules

This part is critical for production.

OTA should use:

Signed firmware
+
Authenticated update source
+
Version validation
+
Integrity verification
+
Rollback protection

The app should never simply accept an arbitrary .bin file and install it on a production device.

The UI does not need to explain cryptography, but the backend/firmware implementation must enforce it.

25. Don't Allow Downgrade Casually

Example:

Current version
1.2.0


Available
1.1.0

Don't offer:

Downgrade

normally.

If rollback is required for support, make it an advanced recovery mechanism with explicit authorization.

28. Repository Architecture

Create:

UpdateRepository
├── getCurrentVersions()
├── checkForUpdates()
├── getUpdateDetails(target)
├── prepareUpdate(target)
├── startUpdate(target)
├── getUpdateProgress(target)
├── cancelUpdate(target)
└── getUpdateHistory(target)

Each mutation should return explicit results:

success
unsupported
unauthorized
unavailable
failed

This matches your existing repository architecture.

29. Preview Release Behavior

Because your current firmware/backend doesn't yet have the complete production OTA infrastructure:

Supported now

Actual firmware installation
Actual OTA transfer
Actual reboot verification
Actual rollback

Until those exist, show:

Don't let a fake Update now button pretend that an ESP32 was actually updated.
