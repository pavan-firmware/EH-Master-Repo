Help & Support Nested Screen Implementation Plan

When the user taps:

Settings → Help and support

this should open a dedicated Help & Support screen.

The purpose is:

Help the user solve common EH Home problems quickly, then provide a clear path to contact support when self-help is not enough.

It should be much more useful than simply displaying a list of FAQ links.

1. Navigation
Settings
   ↓
Help and support
   ↓
HelpSupportPage

Use one reusable:

HelpSupportPage

Back:

HelpSupportPage
      ↓
Settings

Keep Settings selected in the bottom navigation.

2. Header

Use the same nested-screen visual language:

←   Help and support

Subtitle:

Get help with your home, devices, and EH Home.

Keep it simple.

3. Primary Search

This should be one of the most important controls.

┌─────────────────────────────────────┐
│ 🔍  What can we help with?          │
└─────────────────────────────────────┘

Examples of searches:

"Device is offline"
"How do I add a device?"
"Bluetooth won't connect"
"Change Wi-Fi"
"Create a routine"
"Firmware update"

The search should search your structured help content, not arbitrary app strings.

├── Routine not running
└── Maintenance

Don't display irrelevant help articles.

21. Important Safety Handling

Your Help system must be extremely careful with safety-related devices.

For example, for a gas sensor:

Do not say:

The sensor is probably fine.

Instead:

Gas sensor status unavailable


The sensor has not reported recently.
Its current safety state cannot be confirmed.


Follow the safety instructions for
your physical device and environment.


[ Check device ]

Help content should never override the product's safety instructions.

22. Emergency / Critical Event Behavior

If a safety-critical event is active, Help should not become the primary action screen.

Example:

Gas detected


Follow your product's emergency
safety instructions.


[ View safety information ]

Do not bury critical guidance inside ordinary FAQs.

24. Search Architecture

Don't put:

if (query.contains("wifi"))

throughout your widgets.

Use a search layer:

HelpSearchService

that searches:

title
keywords
summary
category
supportedDeviceTypes

This will make the feature scalable.

25. Context Model

HelpContext

├── selectedDeviceId?
├── selectedRoutineId?

├── connectionState
└── deviceState

Then:

HelpContext
    ↓

        ↓

"Device offline"

This is much better than generic search results.

26. Support Safety

Do not let users submit arbitrary diagnostic data automatically.

The support flow should clearly say:

Diagnostics


We can include device and connection
information to help diagnose the problem.


[ View what will be shared ]

Then:

Included:
✓ Device model
✓ Firmware version
✓ Connection state
✓ Recent error codes


Not included:
✓ Wi-Fi password
✓ Security keys
✓ Personal account password

This is a strong privacy design.

Show article skeletons or:

29. Offline Help

One important advantage:

Basic help content should ideally be available offline.

For example:

Bluetooth troubleshooting
Device offline
Factory reset guidance
Add device basics

can be bundled with the app.

If cloud help is unavailable:

You're offline


Basic help is still available.

This is particularly useful for a smart-home app where the user may be offline precisely because something is broken.

Final production principle

The best EH Home Help experience should be:

Search → Understand → Take action → Recover

not:

Search → Read a long FAQ → Figure it out yourself.

And because this is an IoT product, Help should always be connected to the actual device state and available capabilities, while never exposing unnecessary technical details or making unsupported claims.
