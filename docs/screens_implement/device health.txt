Device Health Nested Screen Implementation Plan

When the user taps:

Settings → Device health

open a dedicated Device Health screen.

The purpose is:

Give the user one trustworthy view of device connectivity, freshness, warnings, and basic health—without exposing unnecessary engineering details.

This should be a diagnostics and health overview, not another Devices management page.

1. Navigation
Settings
   ↓
Device health
   ↓
DeviceHealthPage

Use one reusable screen:

DeviceHealthPage(home)

Back:

Device Health → Settings

The bottom navigation remains on Settings because this is a nested Settings screen.

2. Header

Use the same nested Settings pattern:

←   Device health                         ?

Subtitle:

Check device connections and care for your home.

Optional help icon:

?

opens a short explanation:

Device health shows connection status, recent communication, and issues that may need your attention.

Do not use technical terminology in the default UI.

7. Put Problems First

If there are many devices, don't make the user scroll through healthy devices to find a problem.

Recommended ordering:

1. Critical
2. Attention
3. Offline
4. Stale
5. Updating
6. Healthy

Example:

NEEDS ATTENTION
Kitchen air sensor
Offline


OTHER DEVICES
Living room light
Online


Temperature sensor
Online

This is much more useful than alphabetical ordering for a health screen.

Keep healthy information compact.

Living Room
● Online · Updated just now

GPIO state

Those belong in advanced diagnostics.

10. Offline Device

Use clear language:

● Offline

6:35 PM

Don't say:

because the actual issue is connectivity.

11. Stale Device

This is an important distinction.

Example:

Temperature sensor
Living Room


● Connected


Last updated
28 minutes ago


⚠ Data may be outdated

The device may still be reachable, but its data is stale.

Do not call it fully healthy.

12. Unknown Device State

If the system cannot establish the current state:

State unavailable


We haven't received a recent
update from this device.


Last update
Unknown

This is better than guessing:

Offline

or:

Healthy
13. Safety Device Handling

For sensors such as:

Gas sensor
Smoke sensor
Water leak sensor

use stricter messaging.

Example:

Kitchen gas sensor


Current status unavailable


The sensor has not reported recently.
Its current safety state cannot be confirmed.


Last update
6:35 PM


[ Check device ]

Never show:

Safe

when the safety telemetry is stale or unavailable.

This rule should be enforced at the domain layer, not just visually.

18. Don't Overstate "Health"

Be careful with language.

Instead of:

Everything is healthy

when you only know connectivity:

Use:

All devices are online

If you have actual health checks:

No issues detected

Only say:

Healthy

when the underlying system has enough evidence to justify it.

19. Last Checked

At the summary level:

Last checked just now

Last checked 18 min ago

If unavailable:

Health check unavailable

This builds user trust.

23. Troubleshooting

3. Check your home connection.
4. Try reconnecting the device.

24. Connection Architecture

Your Device Health screen should distinguish:

Device connected
Device reachable
Telemetry current
Home connected

These are different states.

For example:

Device
● Online


Telemetry
⚠ Updated 30 min ago


Home
● Connected

The device may be online while its sensor data is stale.

34. Routines Integration

If a required device becomes unavailable:

Device Health
   ↓
Mist maker offline
   ↓
Routine availability
   ↓
Plant care
   ↓
Partially available / unavailable

So the Routines screen can show:

Device unavailable

without duplicating health detection logic.

35. Rooms Integration

Rooms should consume the same device state.

Example:

DeviceHealthRepository
        ↓
Kitchen air sensor = offline
        │
        ├── Device Health → Offline
        ├── Rooms → Kitchen → 1 issue
        ├── Home → 1 device needs attention
        └── Activity → Device went offline

This is an important architectural rule:

One source of truth for device health.

Don't independently calculate device status on every screen.

37. Production Rules

For EH Home, these rules should be mandatory:

Online ≠ Healthy


Online ≠ Fresh telemetry


Offline ≠ Sensor unsafe


Unknown ≠ Healthy


Stale safety data ≠ Safe


Last known state ≠ Current state

And:

Device Health
      ↓
single source of truth
      ↓
Home
Rooms
Routines
Activity
Device Detail

That is the architecture I would use.

The key production decision is to make Device Health the authoritative interpretation layer for device connectivity/freshness, while the actual raw device state remains owned by your device/backend repository. That prevents Home, Rooms, Routines, and Activity from developing conflicting definitions of what “online,” “offline,” or “healthy” means.
