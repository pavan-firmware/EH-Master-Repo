“Connect your home” Nested Screen Implementation Plan

When the user taps:

Settings → Connect your home

this should open the Home Connection / Setup flow.

The main purpose of this screen is:

Show how the EH Home app is connected to the user's home, help complete missing connections, and clearly separate Bluetooth discovery from Wi-Fi/home connectivity.

This screen should not assume that every product uses a Hub. Your current architecture has an ESP32 Node, while Hub functionality can be added later. So the UI should be transport-independent.

22. Existing Device Setup Reuse

Important architectural decision:

Do not duplicate device provisioning logic between these two screens:

Settings
→ Add a room device


Settings
→ Connect your home

Shared Device Commissioning Engine
               │
       ┌───────┴───────┐
       ▼               ▼
Add Room Device    Connect Home

Both can use:

DeviceDiscoveryRepository

WiFiProvisioningRepository

This will prevent bugs where one setup flow works differently from the other.

23. Difference Between “Add Device” and “Connect Home”

This distinction is important in your product.

Add a room device

Purpose:

Add one specific physical device.

Flow:

Discover
→ Select node
→ Verify
→ Configure
→ Assign room
→ Finish
Connect your home

Purpose:

Establish the home's overall connection.

Flow may involve:

Discover/verify
→ Configure home connectivity
→ Wi-Fi
→ Confirm home connection
→ Synchronize devices

Don't make the two screens appear identical.

They share infrastructure but have different user goals.

34. Production rules

The most important rules for this screen are:

BLE connected
    ≠
Home connected
Wi-Fi credentials accepted
    ≠
Home connected
One device online
    ≠
Entire home healthy
Flutter local state
    ≠
Confirmed device state

The final state should only become:

✓ Home connected

after the actual connection flow has been confirmed by the device/backend architecture.

Final user experience

The user should experience this as:

Connect your home → Find/verify device → Connect Wi-Fi → Confirm connection → Done

while underneath, EH Home can handle:

BLE → secure authentication → provisioning → Wi-Fi → device confirmation → repository update → Activity event → Home/Rooms/Routines state refresh.

That gives you a clean production foundation for the current ESP32 Node and leaves room for a future Hub without forcing Hub-specific assumptions into the Flutter UI.
