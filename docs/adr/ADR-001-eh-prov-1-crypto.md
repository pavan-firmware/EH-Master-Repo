# ADR-001: EH-PROV/1 Secure BLE Commissioning & mTLS Device Registration Protocol

- **Status:** `ACCEPTED`
- **Date:** 2026-08-25
- **Author:** EH Home Security & Firmware Architecture Team
- **Relevant Components:** `docs/architecture`, `firmware/common`, `firmware/platforms/esp32`, `backend`, `smart_home_application_v1`, `packages/contracts`

---

## 1. Context & Problem Statement

Phase 5A introduced the baseline provisioning session lifecycle (`CREATED` → `AUTHENTICATED` → `PROVISIONED` → `COMPLETED`), QR code payload parsing (`EH1:<payload>`), device claim domain services, and in-memory mock testing.

However, Phase 5A left critical cryptographic gaps:
1. **Unverified Proofs**: `appProof` and `deviceProof` were accepted as string parameters without cryptographic verification.
2. **Plaintext Backend Secret Exposure Risk**: The backend must not store `commissioningSecret` or Wi-Fi passwords, nor decide that the device is cryptographically authenticated over BLE.
3. **Transport Security Gaps**: Wi-Fi credentials need authenticated encryption over BLE to prevent passive eavesdropping or active ciphertext tampering.
4. **Device Registration Authentication**: After Wi-Fi connection, the device must authenticate itself directly to the backend over HTTPS without relying on app relay or unauthenticated headers.

---

## 2. Decision

We adopt the **EH-PROV/1** protocol architecture for end-to-end commissioning and registration:

### A. Trust Boundary & Secret Treatment
- **App ↔ Device Direct Cryptographic Handshake**: The app scans the QR code containing `deviceId` and `commissioningSecret`. Ephemeral authentication and session key derivation occur strictly between the Flutter App and the ESP32 over BLE.
- **Backend Role**: Excluded from BLE cryptographic trust. Backend handles session metadata, mTLS certificate validation, registration state, and claim mapping. Backend NEVER receives `commissioningSecret`, `sessionKey`, or Wi-Fi passwords.
- **`commissioningSecret` Lifecycle**: Retained securely in flash-encrypted NVS alongside `commissioningSecretConsumed`. Set to `true` ONLY after successful authenticated device registration via mTLS with the backend. Restored ONLY via physical factory reset.

### B. Cryptographic Primitives & Canonical Encoding
- **Authentication**: **HMAC-SHA256** using `commissioningSecret` as key and a byte-level canonical transcript.
- **Key Derivation**: **HKDF-SHA256** (RFC 5869) using `commissioningSecret` as IKM, `appChallenge || deviceChallenge` (64 bytes) as salt, and `"EH-PROV/1|WIFI|" || sessionId || "|" || deviceId` as info. Produces a 256-bit `sessionKey`.
- **Encryption & Integrity**: **AES-256-GCM** with a 12-byte random nonce and 16-byte authTag. AAD is bound to the canonical transcript header for message sequence 4.
- **Canonical Transcript Byte-Level Encoding**:
  - `protocolVersion`: `uint8_t` len (9) + UTF-8 bytes `"EH-PROV/1"`
  - `messageType`: `uint8_t` len + UTF-8 bytes (e.g., 9 for `"APP_PROOF"`)
  - `sessionId`: 36 ASCII bytes (UUID string with hyphens)
  - `deviceId`: 36 ASCII bytes (UUID string with hyphens)
  - `appChallenge`: 32 raw binary bytes (generated by app CSPRNG)
  - `deviceChallenge`: 32 raw binary bytes (generated by device HW RNG)
  - `sequenceNumber`: `uint32_t` Big-Endian (Network Byte Order)

### C. Device-to-Backend mTLS Authentication & Reverse Proxy Boundary
- **mTLS Certificate Authentication**: Device connects directly to backend HTTPS using a per-device X.509 client certificate and ECC keypair provisioned in factory NVS. Client cert is signed by the EH Device Sub-CA.
- **Reverse Proxy Header Boundary**: NGINX / Gateway terminates TLS, validates client certificates against EH Device Root CA (`ssl_verify_client on`), and forwards verified client identity headers (`X-Client-Cert-Fingerprint`) over an isolated Docker network. Backend validates that fingerprint matches `DeviceCredential.tlsClientCertFingerprint`.
- **Production Hardening Requirement**: ESP32 target must enforce **Secure Boot v2** and **Flash Encryption**.

---

## 3. Rationale

- **Threat Model Alignment**: Combines physical QR possession with BLE proximity as the commissioning authorization factor (equivalent to Matter PASE model).
- **Zero Backend Secrets**: Backend database compromise yields no Wi-Fi credentials or raw commissioning secrets.
- **AEAD Integrity**: AES-256-GCM guarantees tampering with ciphertext results in immediate tag rejection before NVS storage.
- **mTLS Device Identity**: Hardware-bound X.509 client certificate ensures only authentic physical devices registered during manufacturing can claim `PROVISIONED` state on the backend.

---

## 4. Alternatives Considered

1. **Backend-Derived Proofs (Phase 5A initial model)**: Rejected because backend would need `commissioningSecret`, violating the zero-secret backend principle.
2. **AES-128-CBC Encryption**: Rejected due to lack of authenticated integrity protection (vulnerable to bit-flipping attacks).
3. **Truncated HMAC as KDF**: Rejected in favor of RFC 5869 HKDF-SHA256 for standard domain separation.
4. **App-Relayed Registration Proof**: Rejected because app could fabricate device connection. Direct mTLS from device guarantees physical device connection.

---

## 5. Consequences & Migration Impact

- **Positive**: Complete end-to-end security matching production smart home specifications.
- **Dependencies**: Adds explicit `pointycastle: ^4.0.0` dependency to Flutter application. Uses standard ESP-IDF mbedTLS (`mbedtls_hkdf`, `mbedtls_gcm`) in firmware.
- **Hardware Requirement**: Hardware validation on physical ESP32 remains **PENDING** until hardware testing phase. Host unit tests cover all crypto logic.
